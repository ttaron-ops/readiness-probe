# A02.3 · Load balancing

> **Concept.** The load balancer is a failure domain and a stateful control point, not a dumb distributor — its health-check logic, hash table, and draining decide whether one slow backend becomes an outage or gets contained.
>
> Module: [🌐 Platform networking depth](../README.md) · Track A — Platform excellence

## Where this fits
Lesson 02 left you at DNS's cache topology — how a name resolves and how that resolution's TTL/staleness interacts with backend churn. This lesson picks up exactly where that hands off: once a client has an IP, the LB is the next stateful control point on the path, and its internal state (health verdicts, hash table, connection table, drain state) determines whether the backend churn DNS just exposed you to turns into a contained blip or a fleet-wide outage. It unlocks Lesson 04's cloud-networking cost model (cross-zone LB is one of the two dominant egress culprits) and Lesson 06's service mesh (Envoy's retry-budget and outlier-detection knobs are the same mechanisms, one layer up the stack).

## Why this matters
At staff scope you own the blast radius, not the box. Every LB decision — how it hashes, how aggressively it health-checks, how it ramps a cold backend, how clients retry — is a lever on whether a transient blip stays a blip or amplifies into a fleet-wide outage. The interview question is never "what is round-robin"; it's "your p99 spiked to timeouts across three services behind one LB tier — walk me through why." Everything below is the mechanism underneath that walk-through, and it's exactly where inference-serving in front of GPU pods diverges hard from stateless web.

## What's new here (calibration)
- **Skipped:** L4 vs L7 in principle, round-robin/least-conn, what a health check is, sticky sessions, anycast basics, and the high-level TLS-termination-location tradeoff.
- **New depth — the algorithm family:** Maglev isn't a one-off trick; it's one instance of "minimal disruption + bounded load imbalance," alongside rendezvous hashing (HRW) and the hashing K8s EndpointSlices themselves use. Knowing the family, not just the Google paper, is the staff-level signal.
- **New depth — the hardware layer underneath the LB:** ECMP at the router is itself a consistent-hash problem with its own reshuffle-on-topology-change failure mode, and it's *why* Maglev's stateless-instance design exists in the first place.
- **New depth — GPU-inference-specific routing:** least-outstanding-requests is table stakes; queue-depth-, KV-cache-, and prefix-cache-aware routing (the llm-d and vLLM data-plane routers) is the current frontier, and it's fair game for a staff interview at a GPU-fleet operator.

## Core concepts

**The LB is a failure domain.** Three pieces of LB state decide blast radius: the *health-check verdict* (which backends are in rotation), the *connection table* (which flows are pinned where), and the *drain state* (what happens to in-flight work on removal). Get any wrong and the LB turns one slow backend into an outage — or contains it. Reason about an LB the way you reason about a database: it has state, that state has failure modes, and the failure modes are correlated across everything behind it.

**Consistent hashing done right — Maglev, and the family it belongs to.** Naive `hash(key) % N` reshuffles *every* flow when N changes (one backend added → ~all flows remap → mass connection resets + cold caches everywhere). Ring/ketama consistent hashing bounds churn to ~1/N of flows on a membership change, but pays with load imbalance (uneven arc lengths → hot backends) unless you add many virtual nodes. **Maglev** (Google's L4 LB) builds a fixed-size *lookup table* via a permutation-fill algorithm that is simultaneously *minimally disruptive* (a single backend change perturbs only its share of table entries) **and** near-perfectly balanced (entries spread within ~1% across backends). It layers *connection tracking* on top so existing flows survive backend-set changes even when the table entry moves — the table decides new flows, the conn-track table protects established ones.

This is one member of a broader family solving the same "minimal disruption, bounded imbalance" problem: **rendezvous hashing** (highest-random-weight, HRW) picks the backend that maximizes `hash(key, backend)` per request — no table at all, O(N) per lookup but trivially consistent and simple to reason about — and **Kubernetes' own EndpointSlice hashing** (used by kube-proxy/IPVS and by topology-aware routing) applies the same principle to Service-to-endpoint mapping. Naming the family — "Maglev's variant of the minimal-disruption hashing problem" — rather than treating Maglev as a one-off algorithm is the concrete staff-vs-senior tell here.

*Table sizing matters.* Production Maglev tables use a size **M much larger than backend count N, and prime** — commonly **M = 65537**. If M is too close to N, the permutation-fill algorithm can't spread entries near-uniformly and the balance guarantee degrades; a large prime M keeps every backend's preference list roughly non-overlapping with every other's, which is what produces the ~1% balance in practice, not just in the average case.

**DSR + ECMP — scaling past one box's bandwidth, and the hardware-level hashing problem underneath.** A single LB is a bandwidth ceiling. The escape: the router does **ECMP** (equal-cost multipath) hashing to spray packets across a *tier* of stateless LB instances — any instance can handle any packet because Maglev tables are deterministic from the same backend set. But ECMP hashing is *itself* a consistent-hashing problem, running on router silicon instead of software, and it has the same reshuffle failure mode: if a router in the ECMP set dies or a link flaps, the router's ECMP group changes and flows rehash across the *surviving* paths — including flows that didn't need to move. This is precisely why LB instances sitting behind ECMP must be stateless: a flow can land on a different LB instance after any topology change, and only a design like Maglev's (deterministic table from the same backend set, connection tracking for flows already pinned) tolerates that without a fresh wave of resets.

Each LB then does **DSR** (direct server return): it encapsulates/rewrites the packet to a chosen backend, but the backend replies *directly to the client*, source-addressed as the VIP, bypassing the LB on the return path. Since responses are the bulk of the bytes (and for inference, the *generated tokens*), the LB tier only sees the thin request path — you scale throughput horizontally by adding LB instances behind ECMP without any single box carrying return traffic. The catch: DSR changes the trust model. Because the backend must source-address its replies as the VIP — not its own address — an in-path firewall, a cloud provider's anti-spoofing check, or NAT can silently drop that return traffic unless it's explicitly allow-listed for the VIP range. "DSR is just a speed trick" undersells it; it's a security/trust-boundary decision as much as a performance one.

**Health checking is subtle, and outlier detection has its own false-positive failure mode.** *Active* checks probe endpoints; *passive* checks (outlier detection) eject backends that return errors on real traffic. The cascading-failure risk: aggressive checks against a *shared dependency* — a backend DB blips, all backends fail their check together, the LB ejects a majority, the survivors get crushed, they fail too. The guard is the **panic threshold** (Envoy default 50%): if fewer than X% of hosts are healthy, the LB *ignores health status entirely* and load-balances across all hosts — betting that a half-degraded backend beats sending 100% of traffic to a collapsing minority.

Passive outlier detection has the opposite-direction failure mode: under *low* traffic, a handful of 5xxs on one backend can look statistically damning even though the backend is healthy — ejecting it on noise. Production Envoy deployments tune `min_request_amount` (don't eject until a backend has seen enough requests to make the error rate meaningful) and `enforcing_success_rate` (what fraction of the time the success-rate outlier check actually acts on its own verdict, letting you dial in sensitivity) precisely to avoid ejecting healthy hosts during quiet periods. Panic mode and outlier tuning are two sides of the same "don't let health-check machinery amplify a small signal into an outage" problem.

**Thundering herd, slow-start, and drain ordering.** On *scale-up*, a fresh backend has cold caches, cold JIT, empty connection pools — give it full share the instant it's `Ready` and it tips over. Envoy's `slow_start_window` linearly ramps its weight from near-zero over the window. On *scale-down*, resets are prevented by ordering: `preStop` hook → endpoint removal → **connection draining** (finish in-flight, refuse new) → `terminationGracePeriod` → SIGKILL; get the ordering wrong and you reset live connections. And the classic: after any blip, *synchronized retries* create a thundering herd — 1000 clients that all failed at T=0 all retry at T=1. **Full-jitter exponential backoff** (`sleep = random(0, min(cap, base·2^attempt))`) is non-negotiable precisely because it de-correlates that spike; plain exponential backoff still lets everyone retry in lockstep.

Crucially, the LB side (panic mode, outlier detection, slow-start) is only half the system. A perfectly-tuned LB in front of clients that retry aggressively without jitter still produces a storm — the LB can only shape *how* it routes load, not *how much* load arrives. This is the same coin as Lesson 06's Envoy retry budgets: a retry budget caps the fraction of a backend's traffic that's allowed to be retries (e.g., 20% of active requests), which bounds the herd at the client-side proxy instead of relying on every client independently implementing jitter correctly. Think of LB-side degradation logic and client-side retry discipline as two halves of the same amplification problem, not two unrelated features.

## Perspectives

**Distributed-systems theory.** Maglev is not "the" answer to consistent load distribution — it's one point in a design space trading off lookup cost, memory, disruption bound, and balance quality. Rendezvous hashing (HRW) gets you consistency with zero shared table state at the cost of O(N) per-lookup work; Maglev trades a bit of memory and a build step for O(1) lookups and near-perfect balance; K8s EndpointSlice hashing applies the same family of ideas to a completely different layer (Service endpoint selection rather than L4 flow routing). A staff engineer should be able to name which member of the family a given system uses and why, not just recite "Maglev" as a keyword.

**Client behavior.** An LB's health-check and panic-mode logic is a policy for how the *server side* degrades. It only produces a good outcome in concert with how the *client side* behaves under failure. A textbook-perfect panic threshold paired with clients that retry every failed request instantly and without jitter still collapses the fleet — the LB spreads load evenly across a degraded set, and the clients immediately multiply that load through synchronized retries. This is why Envoy retry budgets (Lesson 06) exist as a client/proxy-side complement to LB-side health logic: the two need to be reasoned about as one system, and an interviewer probing "why did the outage get worse after the first blip" is testing exactly this connection.

**Hardware and ECMP.** It's tempting to treat "the load balancer" as the software process and stop there, but the router doing ECMP hashing upstream of the LB tier is running the same class of algorithm, in silicon, with its own failure mode: lose a router or flap a link, and ECMP's hash-over-active-paths reshuffles flows across the surviving set — including flows that never touched the failed path. That reshuffle is invisible from inside the LB software; it looks like "some connections just reset for no reason." Recognizing that the failure domain extends one layer below the LB process, into the routing fabric's own hashing, is what separates "I know Maglev" from "I know why Maglev's design choices exist."

**GPU-inference-specific.** For stateless web traffic, least-outstanding-requests is close to optimal and further sophistication has diminishing returns. For LLM inference, request cost varies enormously (prefill vs. decode, prompt length, whether a prefix is cached), so the routing decision itself becomes a scheduling problem: queue-depth-aware routing accounts for backlog, not just in-flight count; KV-cache-aware and prefix-cache-aware routing (the direction projects like llm-d and vLLM's internal data-parallel router are pushing) route a request to the replica that already holds the relevant KV cache or prompt prefix, trading a small routing-locality cost for a much larger compute saving. This is an active frontier, not settled practice — a staff candidate at a GPU-fleet operator should be able to describe *why* prefix-cache-aware routing matters (avoiding recomputation of a shared system prompt or long context across replicas) even without having shipped it.

## Worked example
**Thundering-herd amplification.** 1000 clients, one backend blips for 2s. Model synchronized retry with fixed exponential backoff (1s, 2s, 4s...) vs full jitter.

- *No jitter:* all 1000 fail at T=0, all retry at T=1 (spike = 1000 req in one instant), the retries themselves overload the recovering backend → they fail again → retry at T=3 (another 1000-spike). Retry amplification: offered load = `clients × (1 + retries)` concentrated in instants. The backend never gets a quiet window to recover — a self-sustaining retry storm.
- *Full jitter:* each client sleeps `random(0, 2^attempt)`. The 1000 retries smear uniformly across a 1–2s window → instantaneous rate drops from 1000/instant to ~1000/window ≈ a flat, absorbable trickle. This is the AWS Builders' Library simulation: full jitter both flattens the peak *and* reduces total work, because early successes stop retrying before the herd re-forms.

**Maglev vs modulo remap count.** 1000 flow-keys, backends 3→4.
- *Modulo:* `hash(k) % 3` vs `hash(k) % 4`. A key stays put only if `h%3 == h%4`; that overlap is small, so expect **~700–800 of 1000 flows remap** (mass reset + cold caches everywhere).
- *Maglev:* build the lookup table (size M, a prime like 65537 in prod; use e.g. 7 for a hand exercise) via permutation fill for 3 backends, then for 4. A key remaps only if its table slot changed owner. Adding the 4th backend claims ~M/4 of slots evenly from the existing three → expect **~250 of 1000 flows remap** (≈1/N), and *those* are protected by conn-tracking if already established. Count both, tabulate the delta — that delta is why every serious L4 LB uses a Maglev-style table.

**ECMP reshuffle, for comparison.** Same 1000 flows, but now imagine they're spread across 8 ECMP-hashed paths to the LB tier and one path dies. ECMP typically rehashes over the *remaining* 7 paths using the same hash function, which — depending on the hash's sensitivity to the path count — can remap a large fraction of *all* flows, not just the ~1/8 that were on the dead path, unless the router implements resilient hashing. Contrast this explicitly with the Maglev table result above: the LB layer bounds disruption to ~1/N by design, but the ECMP layer underneath it may not, unless you've specifically checked for and enabled resilient ECMP hashing on the router/switch silicon.

## Common pitfalls
- **"Consistent hashing means zero disruption."** It bounds disruption to roughly 1/N of flows on a membership change — it does not eliminate it. Every backend add/remove still remaps some flows; the win is proportionality, not immunity.
- **"Health checks alone determine rotation."** Panic mode exists specifically because that's false under mass-unhealthy conditions: below the panic threshold, the LB ignores health status entirely and spreads load across everyone, degraded or not. Health status governs the *normal* case, not the *collapse* case.
- **"Round-robin is fair."** It's fair in request *count*, not request *cost*. For heterogeneous-cost workloads — GPU inference above all — equal request counts produce wildly uneven real load, since a 20-token completion and a 4000-token generation can differ 100× in occupancy time.
- **"Exponential backoff without jitter is sufficient."** Exponential growth alone doesn't break synchronization — clients that all failed at the same instant retry in lockstep at every subsequent attempt regardless of how fast the interval grows. Only randomization (jitter) de-correlates the herd.
- **"DSR just means faster."** DSR changes the trust and security model, not just the performance profile: the backend must source-address its replies as the VIP, which can silently break under cloud anti-spoofing checks, in-path firewalls, or NAT unless explicitly allow-listed. Treat it as a network-security design decision, not a pure optimization.

## Self-check
- Why does least-*outstanding-requests* routing matter far more for GPU inference than for a stateless web tier, and what failure does round-robin/least-conn produce there? **Answer:** GPU inference requests have wildly variable cost — a 20-token completion vs a 4000-token generation can differ 100× in occupancy time. Round-robin ignores cost entirely and least-*connections* only counts open connections, not work-in-flight, so both let long generations pile onto some H100s while others sit idle — you get simultaneously queued *and* underutilized GPUs. Least-outstanding-requests (or explicit queue-depth-aware routing) tracks actual in-flight work per replica, so it steers new requests to the genuinely least-loaded GPU and keeps the expensive fleet evenly saturated.
- What does Envoy's panic threshold do, and what cascading failure is it designed to prevent? **Answer:** When the fraction of healthy hosts drops below the threshold (default 50%), Envoy stops honoring health status and load-balances across *all* hosts. It exists to prevent a shared-dependency cascade: if a common backend blips and most hosts fail their health check simultaneously, ejecting the majority would slam 100% of traffic onto a tiny surviving set that then also collapses. Panic mode bets that spreading load over a half-degraded fleet beats guaranteeing the healthy minority gets crushed.
- Why is a newly-`Ready` GPU inference replica not actually ready for full traffic, and how does slow-start map to that? **Answer:** `Ready` (passing a health check) does not mean the model weights are loaded, the CUDA context is warm, the KV-cache allocator is primed, or JIT/graph capture is done — a replica can pass a liveness probe seconds before it can serve at full rate. Give it full share instantly and it queues/tips over. `slow_start_window` ramps the replica's traffic weight up linearly over a window sized to the model-load warmup, so it absorbs the cold-start penalty at low load and reaches full share only once genuinely warm.
- Why must LB instances sitting behind an ECMP tier be stateless, and what does a dead upstream router do to the flows that weren't even routed through it? **Answer:** ECMP hashing at the router chooses which path (and therefore which LB instance) a packet takes based on a hash over the active path set. When a router or link in that set fails, the router rehashes over the *surviving* paths — which, depending on the hash function's sensitivity to path count, can reassign flows that were never on the failed path to a *different* LB instance than before. A stateful LB would have no record of those reassigned flows and would drop or mishandle them; a stateless, Maglev-table-driven LB recomputes the same deterministic backend choice regardless of which instance the packet lands on, so the reassignment is harmless.
- Why does production Maglev use a table size M (like 65537) that's much larger than the backend count N, and why prime? **Answer:** The permutation-fill algorithm needs each backend's preference sequence over table slots to be close to non-overlapping with every other backend's for the near-uniform balance guarantee to hold. If M is too close to N, there isn't enough table space for that near-uniform spread to emerge, and balance degrades toward the modulo case. A large prime M keeps the per-backend permutations well-distributed regardless of N, which is why production deployments fix M at a large prime (65537) rather than sizing it relative to the current backend count.
