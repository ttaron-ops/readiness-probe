The one that is never recoverable

XID 64 — INFOROM_PAGE_RETIREMENT_FAILURE. The remap could not be recorded, meaning the self-repair path itself failed. Cordon, drain, RMA — and do not uncordon.

Contrast XID 63, the same machinery succeeding: a remap entry was recorded but is not yet active. Cordon, drain, schedule a reset window, verify the pending flag clears.

Part twothree meanings

“Recoverable” means three different things

Conflating them is how people build broken runbooks.

LevelThe questionWho decidesWhat you observe
Context-recoverable Did the fault stay inside the faulting CUDA context? hardware containment + driver XID 94 vs 95 — the app dies, the GPU survives
Reset-recoverable Can a reset or reboot restore full capacity? driver, via the GPU Recovery Action enum GPU_RESET / NODE_REBOOT / DRAIN_AND_RESET
Field-recoverable Can the board return to service at all? remap budget, failure flag, recurrence ROW_REMAP_FAILURE=1, exhausted bank histogram, repeat 79 after reseat
A single XID rarely answers all three

XID 94 answers the first — yes, contained. It says nothing about the third: the same board may be three remaps from exhaustion.

Which is why the operational answer is never “look up the XID.” It is “look up the XID, then read the state fields it points at.”

Part threethe discriminator

The same number means opposite things

One pod, XID 31, repeatedly

A user bug. MMU fault — the kernel touched an address with no valid page-table entry. Classic CUDA out-of-bounds or use-after-free. Log it, attribute it to the pod, notify the tenant. Do not cordon.

Every pod on GPU 3, XID 31, within minutes

A bad board or bad driver install. Same error number, completely different blast pattern — and the pattern is the discriminator, not the code.

XID 45 is almost always a symptom, not a cause

PREEMPTIVE_REMOVAL means the driver tore down a channel — after a Ctrl-C, an OOM-kill, or a previous XID. If it trails a hardware XID in the log, act on that one and ignore the 45.

Similarly XID 80 (PUSHBUFFER_CRC_MISMATCH) means corrupted data reached the GPU — often from the host side, bad RAM or bad PCIe. Check the host before blaming the board.

Using itdrills

Drill yourself

XID 31 on GPU 3. Cordon?

Not on its own — it is an MMU fault, almost always a tenant's out-of-bounds access. Log it and attribute it to the pod.

But check the blast pattern: if three or more distinct namespaces hit an app-class XID on the same UUID within an hour, that flips to hardware suspicion and should be escalated.

Which XID means "RMA and never uncordon"?

64 — INFOROM_PAGE_RETIREMENT_FAILURE. The remap could not be recorded, so the card's self-repair mechanism itself has failed. No reset helps.

Do not confuse it with 63, which is the same machinery succeeding and needs only a scheduled reset window.

XID 92 fires. Drain the node?

No. It reports that the single-bit ECC rate crossed a threshold — the errors were corrected and nothing is broken. Trend it and schedule pre-emptive maintenance.

Cordoning on a single 92 burns healthy capacity.

XID 94 versus 95 — what changes operationally?

94 is contained to the faulting context: drain gracefully, reset to apply the remap, verify. 95 is uncontained — other contexts may be poisoned, so drain hard and treat co-tenant output as suspect.

Note neither tells you whether the board is field-recoverable; for that you read the remap budget and failure flag.

You see XID 45 right after XID 48. Which do you act on?

The 48. XID 45 is PREEMPTIVE_REMOVAL — the driver tearing down a channel, frequently because of a preceding fault. It is a symptom.

The 48 is an uncorrectable ECC error where data is already wrong: cordon, drain, reset.

XID 74 on GPU 2. Which cards do you inspect?

GPU 2 and its NVLink partner — the fault is on a connection, GPU↔GPU or GPU↔NVSwitch, so the far end matters too.

It also corrupts collectives, which means a training job may produce wrong results rather than failing loudly.

What to keep

  • Sort by actionCordon-and-drain, log-only, informational, RMA. Not by NVIDIA's cause columns.
  • 64 is terminalThe self-repair path failed. RMA, never uncordon. 63 is the same machinery succeeding.
  • Three recoverabilitiesContext, reset, field. One XID rarely answers more than one.
  • Then read the stateThe XID points at fields — remap budget, failure flag, recovery action. Look those up too.
  • Pattern over numberThree distinct namespaces, one UUID, one hour → hardware, whatever the code says.
  • 92 is a trendCorrected errors. Do not cordon on one.
  • 45 and 80 are symptoms45 trails another fault; 80 often means the host, not the card.
  • 74 corrupts silentlyNVLink faults poison collectives — wrong results rather than loud failure. Check the partner.
