MIG is the only sharing mode that gives each tenant a distinct device UUID — which is why it is the only one where per-pod attribution is a join rather than an estimate. The cost is a partitioning geometry with an asymmetry that strands capacity if you pick the obvious layout.

Part onethe asymmetry

Seven compute slices, eight memory slices

This is the single most useful mechanical fact in the lesson, and it is unambiguous in nvml.h: a GPU Instance's placement is expressed on the memory-slice axis, a Compute Instance's on the compute-slice axis. On Ampere, Hopper and Blackwell datacentre parts the memory axis is 8 slices wide while there are only 7 compute slices.

That asymmetry is the source of every stranded-capacity surprise in MIG.

A 3g profile consumes FOUR memory slices, not three

The allocator rounds up to a power-of-two-aligned block. That is why only two 3g instances fit — slices 0–3 and 4–7 — even though 7 ÷ 3 = 2 with a compute slice spare, and why a 3g cannot start at position 1, 2 or 3.

Efficiency zero: MIG mode costs SMs before you partition anything

The full-card 7g profile reports 98 SMs on an A100 whose die has 108, and 112 on an H100 whose die has 132.

A100: 90.7% — MIG costs ~9.3% of the SMs. H100: 84.8% — ~15.2%. So a fully MIG-enabled H100 running one 7g instance is already ~15% smaller than the same card with MIG off. If a tenant needs the whole card, turn MIG off for that GPU — do not hand them a 7g slice.

The one-line decision

Need isolation, an SLO, or a defensible per-tenant bill → MIG. Need throughput from jobs that under-fill the device, and the tenants trust each other → MPS. Need simple density on trusted, bursty, low-stakes work → time-slicing.

Using itdrills

Drill yourself

Why do only two 3g instances fit on a card with 7 compute slices?

Because a 3g profile consumes four memory slices, not three — the allocator rounds up to a power-of-two-aligned block. Two of them take slices 0–3 and 4–7, filling the 8-wide memory axis.

The leftover compute slice has no memory to pair with.

What does 7 × 1g.10gb actually cost you?

Seven instances take seven of the eight memory slices. The eighth has no compute partner and is unallocatable — about 12.9 GB of an 80 GB card, or $0.51/hour at $4.00/GPU-hour: $373/month per GPU.

It maximises instance count and simultaneously maximises stranded framebuffer.

A tenant needs the whole card. Give them 7g.80gb?

No — turn MIG off for that GPU. MIG mode itself costs SMs before any partitioning: an H100's 7g reports 112 of 132 SMs, about 15% of the die gone.

Why is MIG the only mode where attribution is exact?

Each instance gets its own device UUID (MIG-xxxx), and DCGM programs counters per instance. So the metric join is 1:1 with the pod that holds it.

Time-slicing and MPS both hand out annotated GPU-<uuid>::N IDs against one physical device, so one counter value fans out across every holder.

Name the four zero-stranding geometries.

All of them use all 7 compute slices and all 8 memory slices: 1×7g.80gb, 3g.40gb + 4g.40gb, 2×2g.20gb + 3g.40gb, and 2×1g.10gb + 2g.20gb + 3g.40gb (all-balanced) — at 1, 2, 3 and 4 tenants respectively.
