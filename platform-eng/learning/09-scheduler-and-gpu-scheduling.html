One GPU Pod through fourteen extension points — and the two stages whose absence, not whose behaviour, causes the problems you actually hit.

Shape a pipeline, like the informer chain Partial placement Permit is empty by default The model map[ResourceName]int64, and nothing else

The scheduler is not an algorithm, it is a pipeline of pluggable extension points — the same shape as the informer pipeline from 02.4, and with the same property that each stage has its own distinct failure mode. Tracing one GPU Pod through it explains both why gang scheduling needs a plugin and why the scheduler cannot see your NVLink topology.

Part onethe pipeline

One GPU Pod, every extension point

Following one replica of a training job requesting nvidia.com/gpu: 4, on a 200-node cluster of which 24 have GPUs.

Scheduling cycle — serial, one Pod at a time, no blocking I/O
PreEnqueueRuns before the Pod is admitted to activeQ. Default: SchedulingGates — a Pod with non-empty schedulingGates never enters the queue and gets no Unschedulable condition.GPU fate: where Kueue-style gating could live. Kueue instead suspends the Job, so no Pod exists at all.
QueueSortExactly one plugin cluster-wide (PrioritySort). Orders activeQ.GPU fate: a high-priority training job jumps ahead of inference.
PreFilterCompute Pod-level facts once instead of per node. NodeResourcesFit sums scalar requests here into a state shared by every Filter call.GPU fate: the “4” becomes an int64 in a map. Nothing about card model, memory, or NVLink topology is present.
FilterThe predicate stage. Per node, boolean, across parallelism goroutines (default 16). Any plugin returning Unschedulable removes the node.GPU fate: 176 CPU-only nodes fail with “Insufficient nvidia.com/gpu”. Of 24 GPU nodes, 17 have ≥4 free. Feasible set = 17.
PostFilterOnly runs when the feasible set is empty. Default: DefaultPreemption — pick victims whose eviction makes one node feasible, set nominatedNodeName, delete them, requeue.GPU fate: skipped here. If it ran: DRA resources are not preemptible — the scheduler will not evict a Pod to free a ResourceClaim.
PreScorePrecompute shared state for scoring. Errors abort the cycle.
ScoreThe priority stage. Every surviving node gets an int64 from every Score plugin. MinScore=0, MaxScore=100.GPU fate: the only place a soft preference lives — “prefer the cheaper card, but take the expensive one if that is what is free.”
NormalizeScoreA plugin rescales its own raw scores into [0,100], then each is multiplied by its weight and summed. Highest total wins; ties broken by reservoir sampling, so equal nodes are chosen uniformly.
ReserveMark resources claimed in the scheduler's in-memory cache, before any API write, so the next Pod in the serial cycle sees them consumed. Paired with Unreserve, which runs in reverse plugin order on failure.GPU fate: DRA tentatively allocates a specific device here. Without DRA there is no per-device state — only the integer count.
Permitapprove | deny | WAIT(timeout). “Wait” parks the Pod without releasing its Reserve.GPU fate: the hook gang scheduling uses — hold Pod 1 of 32 until the other 31 reach Permit, then release together. The default profile has no plugin here, which is exactly why partial placement happens out of the box.
Binding cycle — asynchronous, concurrent across Pods
PreBindWork that must succeed before binding, and may do I/O. VolumeBinding provisions PVCs here. Failure → Unreserve everything and requeue.GPU fate: the DRA plugin writes the finalized allocation into ResourceClaim.status — the first time the device decision leaves the scheduler's memory.
BindWrites the Binding object, setting .spec.nodeName. First Bind plugin to handle it wins.
PostBindInformational cleanup. Cannot fail the scheduling.
kubeletNotices a Pod carrying its nodeName — and now the device-plugin machinery decides which physical cards this Pod gets.GPU fate: the scheduler never knew and never will.
The single most important line in the lesson

The scheduler picks a node; the kubelet picks the devices.

Without DRA, no component that made the placement decision knows which physical GPU the container ended up with, which NUMA node it hangs off, or whether the four cards it got are NVLink-connected peers or four strangers on different PCIe roots.

Two stages worth memorising for their absences

PostFilter only runs when the feasible set is empty. If even one node fits, preemption never happens — which is why a cluster with one spare small node will never preempt to make room for a big job.

The default profile has no Permit plugin. That absence is the partial-placement problem: nothing holds Pod 1 of 32 while the rest catch up, so a gang binds piecemeal and strands GPUs.

Part twothe model

What an int64 forecloses

The scheduler's entire model of a GPU is map[v1.ResourceName]int64. NodeResourcesFit sums the scalar requests in PreFilter and checks each against allocatable − requested in Filter. That is the whole thing — and four hard rules follow, enforced by the API server, not by convention:

RuleConsequence
Integers onlynvidia.com/gpu: 0.5 is rejected at admission. There is no millicore equivalent — which is why every sharing mode in module 04 has to fake it with replicas or slices.
Requests must equal limitsIf both are set for an extended resource they must match; setting only limits copies it to requests. So the requests-vs-limits distinction from lesson 01b.3 does not exist for GPUs.
No overcommitUnlike CPU, the scheduler will never place a Pod whose extended-resource request exceeds what remains.
Not shareable between containersTwo containers in one Pod each requesting nvidia.com/gpu: 1 consume two cards.
Which is the whole motivation for the rest of the stack

An integer cannot express “four cards that share an NVSwitch,” “a card with 80 GB rather than 40,” or “half a card.” Everything built on top — MIG's distinct resource names, time-slicing's replicas, DRA's attribute-based claims, Kueue's admission layer — exists to route around that one int64.

Part threefilter vs score

Why cost is a Score, never a Filter

Filter — the predicate
  • boolean, per node
  • removes nodes from consideration
  • a wrong Filter means Pending forever
  • use for hard requirements
Score — the preference
  • int64 0–100, weighted and summed
  • ranks the survivors
  • a wrong Score means suboptimal, still runs
  • use for soft preferences
The judgement this forces

“Prefer the cheaper GPU” must be a Score. Written as a Filter, a cluster with no cheap cards free leaves the Pod Pending indefinitely rather than running it on an expensive card.

The general rule: if the answer to “would you rather it not run at all?” is no, it is a Score.

Using itdrills

Drill yourself

Why does a distributed job get partially placed by default?

Because the default scheduler profile has no Permit plugin. The scheduling cycle is serial and one Pod at a time, so Pods 1..k bind as nodes are found and Pods k+1..32 stay Pending — holding GPUs the bound Pods cannot use.

Gang scheduling fixes it by adding a Permit plugin that returns WAIT until minMember Pods reach that point, then releases them together.

You want to prefer cheaper GPUs. Filter or Score?

Score. A Filter is a hard predicate — implemented that way, a cluster with no cheap cards free leaves the Pod Pending forever rather than running it somewhere more expensive.

Rule of thumb: if you would not rather the Pod didn't run at all, it belongs in Score.

Which component decides which physical GPU your container gets?

The kubelet, via the device plugin, after binding. The scheduler only chose a node.

So without DRA nothing in the placement path knows whether your four cards are NVLink peers or four strangers on different PCIe roots — which is exactly why topology-aware placement needs machinery outside the default scheduler.

Your cluster has one small free node and a big job stays Pending. Why no preemption?

PostFilter only runs when the feasible set is empty. If any node passes Filter — even one that will never be chosen — preemption never triggers.

Note also that DRA-allocated resources are not preemptible at all: the scheduler will not evict a Pod to free a ResourceClaim.

Two containers in one Pod each request nvidia.com/gpu: 1. How many cards?

Two. Extended resources are not shareable between containers, even inside one Pod. Nor can you request 0.5 — integers only, enforced at admission.

Does the requests-vs-limits distinction mean anything for GPUs?

No. For extended resources, if both are set they must be equal, and setting only limits copies the value to requests.

So the entire weight-versus-cap mechanism from lesson 01b.3 — cpu.weight vs cpu.max — has no GPU analogue at this layer.

What to keep

  • A pipeline, not an algorithmPluggable extension points in a fixed order, each with its own failure mode.
  • Filter is fatal, Score is notA wrong predicate means Pending forever; a wrong preference means merely suboptimal.
  • PostFilter needs an empty setOne feasible node anywhere means preemption never fires.
  • Permit is empty by defaultThat absence is the partial-placement problem, and the hook gang scheduling fills.
  • Reserve is in-memoryBefore any API write, so the next Pod in the serial cycle sees the consumption.
  • Node vs devicesThe scheduler picks a node; the kubelet picks the cards. Without DRA, nobody in the placement path knows which.
  • One int64No fractions, no overcommit, no sharing, requests ≡ limits. Everything in module 04 routes around it.
