The ring all-reduce derived chunk by chunk — and the consequence that adding data-parallel ranks costs you latency but almost no extra bandwidth per GPU.

Key result 2(N−1)/N → 2, and fast Measure with busbw, never algbw Healthy 80–88% of unidirectional spec

NCCL is where "which collective over which link" becomes real wire traffic. Two things are worth owning here rather than quoting: the ring all-reduce derivation — because it explains why data parallelism scales — and bus bandwidth, because it is the only number you can compare against a spec sheet.

Part onethe barrier

Why a collective is a barrier, mathematically

Ordering is enforced by position, not by name

Every rank must call the same collectives, in the same order, the same number of times, with the same sizes and datatypes. Each communicator keeps an opCount that increments per enqueued collective, and operations are matched pairwise by position.

So if rank 5 issues AllReduce, AllGather while everyone else issues AllGather, AllReduce, you get a hang or silently wrong data. Frameworks avoid this by construction — DDP and FSDP issue from the autograd engine in deterministic order — which is why the ordering bugs you actually meet come from conditional code: if rank == 0: log_something_that_all_reduces(), or an early break when one rank's shard runs out first.

Part twothe derivation

The ring all-reduce, step by step

Both naive schemes are bad. Reduce to rank 0 and broadcast back makes rank 0's single link carry ≈2S bytes while every other link idles; all-to-all moves N(N−1) messages. The ring makes every link carry the same load, all the time.

Arrange ranks in a logical ring, split each array into N chunks. Every step, every rank sends exactly one chunk to its successor and receives one from its predecessor.

After N−1 steps each rank owns exactly one fully reduced chunk — that is a reduce-scatter. Phase 2 runs the same ring in the same direction for another N−1 steps, storing rather than accumulating, and every rank ends with every chunk.

The most misunderstood fact about scaling data parallelism

2(N−1)/N = 2 − 2/N. At N=2 it is 1.0, at N=8 it is 1.75, at N=64 it is 1.969, at N=16,384 it is 1.99988. Bounded above by 2, and it gets there fast.

Adding data-parallel replicas does not multiply your per-GPU bandwidth bill. It is asymptotically flat — which is exactly why lesson 08.1 could say the reason to leave DDP is memory pressure, not bandwidth scaling.

What does grow with N is the step count

2(N−1) steps, and therefore the latency floor. Each step is a real hop with a real cost — kernel-side handshake, buffer copy, and on inter-node hops a proxy thread posting an RDMA operation.

Part threemeasuring

algbw versus busbw

Algorithm bandwidth
  • algbw = S / t
  • answers “how long will this take”
  • useless for judging hardware
  • falls as N grows even on a healthy fabric
Bus bandwidth
  • busbw = algbw × 2(N−1)/N
  • corrects for the ring's byte count
  • comparable to a spec sheet
  • independent of rank count
Trap one — busbw can exceed the physical link rate

It is only a wire speed when the algorithm is a flat ring. When NCCL picks a hierarchical algorithm the payload no longer maps onto any single link.

On an 8×H200 node at 16 GiB, all_reduce reports 480.0 GB/s against a 450 GB/s NVLink 4 spec — 107% — because NCCL selected NVLS and the NVSwitch did the reduction. Force the ring with NCCL_NVLS_ENABLE=0 and the same collective reports 367.2 GB/s, 82% of spec, which is the honest wire number.

Trap two — ~80% of spec is the normal, healthy result

Not a problem to chase. Encoding overhead and protocol framing eat the rest. If you measure 80–88% of the unidirectional spec, your fabric is fine.

All-gather and reduce-scatter on that same H200 node report 361.4 and 362.9 GB/s — 80–81% — because they have no NVLS path and always ran the ring.

Using itdrills

Drill yourself

Going from 8 to 512 data-parallel ranks — how much more bandwidth per GPU?

Almost none. Per-rank bytes are 2(N−1)/N · S: 1.75S at N=8, 1.996S at N=512 — a 14% increase, and bounded above by 2S forever.

What grows is the step count, 2(N−1), and therefore the latency floor. Bandwidth is not why you leave DDP; memory is.

Your benchmark reports 107% of the NVLink spec. Is the tool broken?

No — NCCL chose NVLS, so the NVSwitch performed the reduction in-network and the payload never traversed a single link the way the ring formula assumes. busbw's correction factor only describes a flat ring.

Set NCCL_NVLS_ENABLE=0 to get the honest wire number, which will land around 82%.

You measure 82% of the unidirectional spec. Escalate?

No. 80–88% is the healthy range — encoding overhead and protocol framing account for the rest. Chasing the last 18% is chasing physics.

Rank 5 hangs in a collective. What class of bug should you suspect first?

Collective ordering. Operations are matched pairwise by opCount position, not by name — so if one rank issues a different sequence, you get a hang or silently wrong results.

Look for conditional collectives: if rank == 0: branches that call something reducing, or an early break when one rank's data shard runs out first. Framework-issued collectives are deterministic by construction.

Why does the ring have no hot spot?

Because every rank sends exactly one chunk of S/N bytes to its successor in every step, in both phases — so every link carries identical load at every moment.

Compare reduce-to-root-and-broadcast, where rank 0's single link carries ≈2S while every other link idles.

After phase 1, what does each rank hold?

Exactly one fully reduced chunk — chunk (r+1) mod N — and no other chunk completely. That is precisely a reduce-scatter, which is why NCCL implements reduce-scatter as phase 1 alone and all-gather as phase 2 alone, each at N−1 steps.
