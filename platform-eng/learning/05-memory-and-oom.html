Four quantities get called “memory used” and three events get called “OOM”. Separating both sets is the difference between fixing a limit and fixing a leak.

Working set memory.current − inactive_file Victim score a raw page count, not a permille Global OOM QoS decides, not size

Four different numbers get called “memory used”, and only one of them predicts an OOM kill. Three different events get called “OOM”, and they have different blast radii, different signals, and different fixes. This page separates both sets.

Part onethe promise and the bill

Lazy allocation, concretely

mmap(NULL, 8<<30, …) creates a VMA — a record saying “these 8 GiB are readable/writable anonymous memory” — and returns. Zero physical pages have been allocated. The page-table entries are empty. The first write faults, and the handler allocates one 4 KiB frame, zeroes it, and installs a PTE.

malloc returning NULL is a fiction on Linux

The kernel overcommits, so the failure surfaces later, at fault time, in a context — a page fault deep inside a memcpy — where there is nothing sensible to return to the caller. That is why the OOM killer exists at all: allocation failure has no good answer, so the kernel picks a process and SIGKILLs it so the machine keeps running.

The working-set formula, exactly — nearly every blog post gets this wrong

cAdvisor computes it as total cgroup usage minus inactive_file, floored at zero. Not anon + active_file.

The difference matters: usage includes kernel memory charged to the cgroup (slab, kernel_stack, pagetables, sock, percpu), and those are in the working set. Subtracting only inactive_file means the kernel's own “this cache looks cold” verdict is the single thing excluded.

Part threevictim selection

Kill the hog — that is the entire policy

oom_score_adj == -1000 returns LONG_MIN — unconditionally immune. So does an unkillable task, a task already reaped, or one in vfork.

Kubernetes QoS maps straight onto that bias

Processoom_score_adj
kubelet · kube-proxy−999
Node-critical pods · Guaranteed containers−997
Burstable containers1000 − (1000 × memRequest) / memCapacity, clamped to [3, 999]
BestEffort containers+1000

Both clamps carry meaning. The lower clamp is 1000 + (−997) = 3, so a Burstable container can never score better than a Guaranteed one however large its request. The upper clamp turns a computed 1000 into 999, so a Burstable container with a negligible request still dies after BestEffort.

Eviction is the path that is supposed to happen

The kubelet polls working set and starts terminating pods gracefully before the kernel is forced to SIGKILL anything.

A global OOM means the eviction path lost the race — which on a node with fast-growing anonymous allocations (a trainer adding 20 GB in two seconds) it frequently does, because the kubelet's housekeeping interval is on the order of seconds.

Why eviction ranks on working set and not RSS

RSS includes cold file cache the kernel will hand back for free, and counts shared pages once per sharer. Ranking on it would evict a pod that is merely holding page cache — the very thing the kernel is about to reclaim itself — while sparing the pod whose anonymous footprint is the actual problem.

usage − inactive_file removes exactly the pages the kernel has already judged cold, making it the closest cheap proxy for “memory that will still be needed a moment from now.”

memory.oom.group is already on

It tells the kernel to treat the cgroup as an indivisible workload: when OOM fires anywhere in it, every task in it and its descendants dies together, except those with oom_score_adj == -1000. And an OOM firing inside a cgroup will not kill anything outside it, regardless of ancestors' settings.

Using itdrills

Drill yourself

Write the working-set formula exactly.

working_set = memory.current − memory.stat[inactive_file], floored at zero.

Not anon + active_file. Usage includes kernel memory charged to the cgroup — slab, kernel stacks, page tables, sockets, percpu — and those are part of the working set. Only the kernel's cold-file verdict is subtracted.

A 6 GiB Burstable sidecar requesting 32Gi on a 512 GiB node. What is its OOM bias worth?

adj = 1000 − (1000 × 32)/512 = 938, which at global-OOM time adds 938 × 134,217,728/1000 pages ≈ 480 GiB of effective footprint.

Its real 6 GiB is a rounding error beside that. In a global OOM, QoS class decides, not size — which is why matching requests to actual usage is survival advice, not just scheduling advice.

Is oom_score a percentage of memory?

No — that was the pre-2.6.36 heuristic. oom_badness() returns a raw page count: resident pages + swap entries + page-table pages, plus the normalised oom_score_adj bias.

The 0–1000 figure in /proc/<pid>/oom_score is a normalised view of that, not the internal number.

free -m shows 2.1 GB free of 64 GB. Panic?

No. Read available — 50.8 GB here. It is the kernel's estimate of what a new allocation can get without swapping, derived from MemFree, file LRU sizes and SReclaimable minus watermarks and a page-cache reserve.

Large buff/cache is the kernel doing its job, not a leak.

Container exits 137. Which of the three events was it?

Either cgroup OOM or global OOM — both produce OOMKilled and exit 137 (128 + SIGKILL). An eviction shows Evicted with graceful termination instead.

Separate them with memory.events oom_kill and the dmesg text: Memory cgroup out of memory for cgroup scope, Out of memory plus a zone dump for global.

Why did the kubelet not evict before the kernel killed?

It lost the race. The kubelet polls working set on a housekeeping interval measured in seconds; a trainer that adds 20 GB in two seconds crosses from healthy to unallocatable inside one interval.

Eviction is the path that is supposed to happen; a global OOM means it did not get there in time.
