A container is
one clone3() call
with eight bits set

The eight things nsproxy points at, the three syscalls that create, move and join them, and the nine steps runc runs between "start a container" and your entrypoint.

Opens up the nsproxy pointer from 01b.1 Corrects “the cgroup namespace controls resources” Explains why your container ignores docker stop

Lesson 01b.1 ended with a claim: a container is a set of ordinary task_structs whose nsproxy pointer happens to point somewhere private. This is the lesson that opens up nsproxy and shows you the eight things it points at — and the single clone3() call that makes all of them private at once.

Part onethe eight

One flag word, eight independent switches

The namespace flags are clone() flags — bits in one integer, OR'd together. Which is the same shape as __state from lesson 01b.1, and it means "which namespaces does this container have?" is literally a bitmask question.

Two naming accidents worth knowing

Mount's flag is CLONE_NEWNS, not CLONE_NEWMNT, because it was first — there was no need to say which "NS" you meant.

CLONE_NEWTIME's tiny value (0x80) collides with legacy clone(2)'s exit-signal field, so it is only usable via clone3(2) or unshare(2).

The three that get misread

“The cgroup namespace controls resources”

It does not. It virtualises the cgroup root directory as reported in /proc/<pid>/cgroup. Path cosmetics and information hiding — your limits are unchanged, your parent can still see and set them.

Where resource control actually lives

Lesson 01b.3. Nothing about cpu.max or memory.max moves when you create a cgroup namespace. It is the most commonly confused namespace purely because the word “cgroup” is in it.

The IPC namespace does not isolate /dev/shm — and this bites GPU nodes specifically

IPC covers System V objects (what ipcs lists) and POSIX message queues. /dev/shm is a tmpfs mount, so it is isolated by the mount namespace and sized by that mount's size= option.

PyTorch DataLoader with num_workers > 0 passes tensors between workers through /dev/shm. The default 64 MiB in many images produces Bus error or DataLoader worker killed. Fix it with --shm-size or an emptyDir: {medium: Memory} at /dev/shm — not with anything IPC-namespace-shaped.

UTS isolates less than people assume

Exactly struct utsname: hostname and NIS domain. Nothing else. It does not usefully isolate the kernel release string — the container still reports the host kernel, which is the entire point of containers versus VMs.

Part twoPID 1

A task genuinely has several PIDs

The PID namespace is hierarchical. The first process in a new one is PID 1 there and simultaneously has a larger PID in every ancestor namespace — a single task really does hold multiple PIDs, stored in struct pid's numbers[] array.

Three special rules for PID 1 — and the production bug each causes

  1. Signals without an installed handler are not delivered to PID 1

    Not even from a privileged process, not even from an ancestor namespace. Deliberate protection against killing a namespace's init. SIGKILL and SIGSTOP from an ancestor are the exception — those are forcibly delivered.

    This is the mechanism behind "my container ignores docker stop." The runtime sends SIGTERM to PID 1 — your python train.py, which installed no handler — and the kernel drops it. The runtime waits out terminationGracePeriodSeconds (default 30) and then sends SIGKILL, which cannot be ignored.

    The fix is a real init as PID 1 (tini, docker run --init) or handling the signal in your app. Not a longer timeout.

  2. PID 1 is the reaper of last resort

    Any orphaned process in the namespace reparents to PID 1, which must wait() for it or leave a zombie. An app that never reaps accumulates Z entries holding PIDs forever — the zombie mechanic from lesson 01b.1, now with a namespace-scoped owner.

  3. When PID 1 exits, the kernel SIGKILLs every process in the namespace

    Afterwards fork() into that namespace fails with ENOMEM. The namespace is dead even if something still holds it open.

And the network namespace explains the pod model in one line

A net namespace is a complete independent stack — interfaces, routes, nftables, /proc/net, socket tables, and the port number space. A fresh one contains exactly one interface: a lo that is administratively down.

Two containers sharing a net namespace share one IP and one port space. That is precisely why two containers in a Kubernetes pod cannot both bind :8080, and can reach each other over 127.0.0.1.

Part threethe syscalls

Create, move, join

  ┌────────────────────────────────────────────────────────────────────┐
  │  clone(2) / clone3(2)  —  CREATE a process INTO new namespaces     │
  │     new task_struct, new nsproxy with the flagged fields replaced  │
  │     ▸ this is what runc/crun call                                  │
  │     ▸ clone3 also has CLONE_INTO_CGROUP — born directly into a     │
  │       target cgroup, no post-hoc write to cgroup.procs             │
  ├────────────────────────────────────────────────────────────────────┤
  │  unshare(2)            —  MOVE MYSELF into new namespaces          │
  │     no fork; my nsproxy is replaced in place                       │
  │     ▸ EXCEPT CLONE_NEWPID, which only sets pid_ns_for_children     │
  │     ▸ CLONE_NEWUSER is applied FIRST, so one call can gain the     │
  │       privilege it needs to create the others                      │
  ├────────────────────────────────────────────────────────────────────┤
  │  setns(2)              —  JOIN an EXISTING namespace               │
  │     takes an fd on /proc/<pid>/ns/<type>                           │
  │     creates NOTHING; just repoints my nsproxy field                │
  │     ▸ this is what nsenter(1), docker exec, kubectl exec do        │
  └────────────────────────────────────────────────────────────────────┘
Two ordering rules that explain otherwise baffling behaviour

unshare(CLONE_NEWUSER | CLONE_NEWNET) works unprivileged; unshare(CLONE_NEWNET) alone does not. The kernel applies the user namespace first, so by the time it creates the net namespace you already hold CAP_SYS_ADMIN in the new user namespace. This is exactly the primitive that turns "unprivileged user" into "root over a fresh copy of half the kernel's subsystems" — and the reason this area keeps producing CVEs.

unshare(CLONE_NEWPID) does not move you. It sets pid_ns_for_children. unshare(1) papers over this with --fork. Without it your shell stays put and its children land in a namespace whose init is nothing — so the first child to exit takes the namespace down.

What kubectl exec actually does — and what it proves

It opens /proc/<pid>/ns/{mnt,net,uts,ipc,pid} for a process already in the container, calls setns() on each fd, forks (needed for the PID namespace to take effect), and execve()s your command. Nothing is created, no container started, no image pulled.

So: an exec that "works" proves the namespaces are intact. It proves nothing about the application. When you are debugging a wedged pod, exec succeeding tells you the runtime and kernel are fine and the problem is above them.

Part fourconstruction

A container, in nine steps

A container is namespaces + a cgroup + a rootfs. Nothing else. Here is what runc does between "containerd asked for a container" and "your entrypoint is running":

  t0  runc reads config.json (the OCI runtime spec)
      │
  t1  clone3(CLONE_NEWNS|CLONE_NEWUTS|CLONE_NEWIPC|CLONE_NEWPID|CLONE_NEWNET
             [|CLONE_NEWUSER][|CLONE_NEWCGROUP], CLONE_INTO_CGROUP=<fd>)
      │      └── child born into fresh namespaces AND its cgroup, one syscall
      ▼
  t2  [child] write uid_map/gid_map if a user namespace was created
      │        (write-once; before the child drops privilege)
      ▼
  t3  [child] mount the rootfs; make the tree MS_PRIVATE/MS_SLAVE so our
      │        mounts do not escape          ← the propagation reset
      ▼
  t4  [child] bind-mount devices, volumes, /proc, /sys, /dev/shm (tmpfs),
      │        the GPU device nodes and driver libraries
      ▼
  t5  [child] pivot_root(new_root, put_old); umount the old root
      │        ← the ROOTFS half. No namespace involved — just a
      │          mount-namespace-local root swap
      ▼
  t6  [child] set hostname (UTS ns), sysctls, rlimits
      ▼
  t7  [child] attach BPF_PROG_TYPE_CGROUP_DEVICE → device allowlist;
      │        seccomp filter; AppArmor/SELinux label
      ▼
  t8  [child] drop capabilities to the configured bounding/effective set
      ▼
  t9  [child] execve(entrypoint)            ← PID 1 in its namespace
Note what is not in that list

No hypervisor. No VM exit. No special CPU mode. No kernel object named "container."

Everything Docker, containerd and Kubernetes add above this — image distribution, CNI, lifecycle, scheduling — is orchestration around those nine steps.

Which closes the loop from lesson 01b.1

Step t1 is the whole answer to "is a container a single schedulable entity?" It is one clone3() call that produces one task — and every descendant inherits the same nsproxy by reference count. The container is the set that grows from there, and no step in this sequence ever tells the scheduler anything.

Using itdrills

Drill yourself

Your container ignores docker stop and takes 30 seconds to die. Why?

PID 1 does not receive signals it has no handler for — a deliberate kernel rule protecting a namespace's init. Your entrypoint is python train.py with no SIGTERM handler, so the kernel drops it. The runtime waits out the grace period and then sends SIGKILL, which cannot be ignored.

Fix: a real init as PID 1 (tini, --init) or handle the signal. Raising the timeout just makes you wait longer for the same SIGKILL.

Your DataLoader dies with Bus error. Which namespace do you reach for?

The mount namespace, not IPC. /dev/shm is a tmpfs mount, sized by that mount's size= option — the IPC namespace covers System V objects and POSIX message queues, neither of which PyTorch uses here.

Fix with --shm-size or an emptyDir: {medium: Memory} at /dev/shm.

Why does unshare(CLONE_NEWNET) fail unprivileged, but unshare(CLONE_NEWUSER|CLONE_NEWNET) succeed?

Creating a user namespace has required no privilege since Linux 3.8, and the kernel applies CLONE_NEWUSER first. By the time it creates the net namespace you already hold CAP_SYS_ADMIN within the new user namespace.

That single ordering rule is what makes rootless containers possible — and is the root of a recurring class of local privilege-escalation CVEs.

kubectl exec into a wedged pod works fine. What have you learned?

That the namespaces are intact and the runtime and kernel are healthy. exec only calls setns() on existing namespace fds, forks, and execve()s — it creates nothing.

So it proves the problem is above the runtime, in your application. It says nothing about whether the app is functioning.

Does creating a cgroup namespace change what a container is allowed to use?

No. It virtualises the cgroup root directory as reported in /proc/<pid>/cgroup and mountinfo — path cosmetics and information hiding.

Limits are unchanged and the parent can still see and set them. Actual resource control is lesson 01b.3.

Two pods claim to share a network namespace. How do you check?

Compare the inode numbers behind /proc/<pid>/ns/net for a process in each. Same inode means the same namespace — that is the identity, and the cheapest possible membership test.

What to keep

  • Eight bits, one wordNamespace membership is a clone-flag bitmask — the same shape as __state.
  • Create / move / joinclone makes a process into new ones, unshare moves you, setns joins existing ones and creates nothing.
  • Identity is an inodeSame number behind /proc/<pid>/ns/<type> means same namespace.
  • PID 1 drops unhandled signalsThe mechanism behind slow container shutdown. Fix the init, not the timeout.
  • cgroup ns ≠ cgroupPath cosmetics. Resource control is a different subsystem entirely.
  • IPC ns ≠ /dev/shmThat is a tmpfs mount, so it belongs to the mount namespace. The DataLoader bug lives here.
  • User ns firstUnprivileged since 3.8, applied before the others, and the source of the CVE class.
  • Nine steps, no container objectNamespaces + cgroup + rootfs. Everything above is orchestration.
