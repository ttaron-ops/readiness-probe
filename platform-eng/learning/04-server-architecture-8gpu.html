The point of drawing it twice

GPU4 and GPU0 are on opposite sockets in network 1 — topo -m reports SYS between their NICs — and direct neighbours in network 2, where topo -m reports NV18 between the GPUs.

Both statements are true at the same time. They describe different fabrics. Every "but I thought these GPUs were close together" argument is this.

The single most useful line to internalise

GPU–GPU all-reduce inside one node is not affected by NUMA. It is on the NVSwitch fabric. But the moment data leaves a GPU for host RAM, a NIC, or a disk, PCIe and NUMA locality govern it completely.

“Non-blocking” is a per-domain claim

Within one HGX baseboard the domain is 8 GPUs and the fabric is genuinely non-blocking for all-to-all. Extended through external NVLink switches the domain grows — 256 GPUs for H100-generation NVLink Network, 72 in a GB200 NVL72 rack — and the guarantee holds within that boundary.

It is a statement about topology (no cut is worse than the bisection), not a promise that every conceivable pattern runs at peak. Knowing the domain size for the hardware in front of you is part of the fluency.

Part fourrail alignment

Two requirements, both mandatory

The network is organised into rails: NIC k on every node connects to leaf switch k. Rail-aligned means GPU k's traffic egresses on NIC k and lands on rail k's leaf — so a collective between the GPU5s of many nodes stays on one leaf switch and never touches the spine.

  REQUIREMENT 1 — WITHIN THE NODE

    CORRECT   GPU5 ──▶ PCIe switch 3 crossbar ──▶ NIC5 ──▶ wire

      topo -m:  GPU5 <-> NIC5 = PIX (or PXB)
      GPUDirect RDMA: HBM → NIC directly. Host DRAM never touched.
      Cost: one switch hop.   Ceiling: min(63, 50) = 50 GB/s


    BROKEN    NIC5 cabled to a socket-0 slot

      GPU5 ──▶ switch3 ──▶ root port ──▶ socket 1
                        ──UPI──▶ socket 0 ──▶ root port ──▶ switch0 ──▶ NIC5

      topo -m:  GPU5 <-> NIC5 = SYS
      GPUDirect RDMA is NOT a supported fast path across sockets.
      The stack falls back to staging through host DRAM:
         HBM → PCIe → DRAM(node1) → UPI → DRAM(node0) → PCIe → NIC5

      Ceiling collapses to the UPI share:
         ~38 GB/s best case,  ~19 GB/s with a second contending flow


  REQUIREMENT 2 — ACROSS THE FABRIC

    NIC k on EVERY node cables to leaf switch k, consistently, fleet-wide.

    A perfectly aligned single node still loses if cabling is inconsistent
    across nodes: a collective between GPU5s then traverses the spine on
    some node pairs and not others — and the slowest pair sets the
    collective's time.
Using itdrills

Drill yourself

topo -m says SYS between two GPUs' NICs but NV18 between the GPUs. Which is right?

Both. They are readings from two different graphs. SYS describes the PCIe tree, where the GPUs hang off root ports on opposite sockets. NV18 describes the NVLink fabric, where every GPU on the baseboard is one NVSwitch hop from every other.

Which one matters depends entirely on what the traffic is: GPU↔GPU uses NVLink, GPU↔NIC/DRAM/NVMe uses PCIe.

How much faster is H100 NVLink than PCIe Gen5 x16?

7.1× — 450 GB/s versus 63 GB/s, both per direction.

If you answered 14×, you compared NVIDIA's marketed bidirectional 900 GB/s against a per-direction PCIe figure. That is the most common arithmetic error in this subject area.

Does an 8-GPU all-reduce inside one node care about NUMA?

No. It runs entirely on the NVLink/NVSwitch fabric and never touches the CPU or PCIe.

But every byte that goes to host DRAM, a NIC, or an NVMe drive is fully governed by PCIe placement and NUMA locality — so a data loader on the wrong socket still ruins the step time.

A NIC is cabled to the wrong socket's slot. What is the actual throughput cost?

GPUDirect RDMA stops being a supported fast path, so the stack stages through host DRAM and crosses UPI: HBM → PCIe → DRAM → UPI → DRAM → PCIe → NIC.

The 50 GB/s ceiling collapses to the UPI share — about 38 GB/s at best, roughly 19 GB/s if a second misplaced flow contends.

Your node is perfectly rail-aligned internally. Are you done?

No — that is only requirement 1. NIC k must also cable to leaf switch k consistently on every node in the fleet.

If cabling is inconsistent, a GPU5-to-GPU5 collective traverses the spine on some node pairs and not others, and the slowest pair sets the collective's completion time.

Where are the PCIe switches physically, and why does it matter?

On the CPU/motherboard tray, not the GPU baseboard. Each GPU reaches its switch over a Gen5 x16 link carried across retimers to the baseboard.

It matters because NIC and NVMe placement relative to those switches — which is an OEM chassis decision, not a GPU one — determines whether GPUDirect paths stay switch-local.

What to keep

  • Two graphsThe same eight GPUs as PCIe leaves and as NVLink peers. Different fabrics, both readings true.
  • 450, not 900Per direction versus marketed bidirectional. NVLink beats PCIe Gen5 by 7.1×, not 14×.
  • NVLink ignores NUMAIntra-node GPU↔GPU never touches CPU or PCIe. Everything else is NUMA-bound.
  • Switches on the CPU trayGPU links reach them over retimers. NIC/NVMe placement is an OEM decision.
  • Non-blocking is per-domain8 on a baseboard, 256 via NVLink Network, 72 in a GB200 NVL72.
  • PIX good, SYS badCross-socket GPU↔NIC drops GPUDirect RDMA and collapses 50 GB/s to a ~38 GB/s UPI share.
  • Rails need both halvesSwitch-local inside the node and consistent NIC-to-leaf cabling fleet-wide.
  • The slowest pair winsA collective completes when its worst node pair does — so partial alignment buys nothing.
