Part onethe ceiling

Bandwidth ÷ bytes, and nothing else

Each forward pass must read essentially every weight from HBM exactly once — every layer is used, and no weight is reused within a single-token pass. The arithmetic per weight is one multiply and one add.

Quantisation is a throughput lever, not just a capacity lever

Halving bytes per parameter halves bytes read per token and therefore doubles the ceiling: 23.9 → 47.9 tok/s on the same H100, with no hardware change.

That framing is worth carrying into a procurement conversation, where quantisation usually gets discussed only as "does it fit."

Part twothe lever

Why batching works, and where it stops

The weight read is a fixed cost paid once per forward pass. Run a batch of B sequences and you read the weights once but emit B tokens — the matrix-vector products become matrix-matrix products.

But the KV read is not shared. Every sequence has its own cache, and every cache must be read in full. So one decode step is:

Llama-3-70B, FP8 weights and FP8 KV, one H200 (4.8 TB/s, 1,979 TFLOP/s dense FP8). The dashed line is what batching would give if KV were free — pure amortisation of the shared weight read. The gap between each curve and that line is the KV cache. Long contexts leave the ideal almost immediately; short ones track it far longer.

Two separate limits, often confused

Capacity — you run out of VRAM for KV, so you cannot admit more sequences. That is 07.2's concurrency cap.

Rate — you can still admit them, but each one adds more KV read time than it adds throughput. That is this lesson, and it bites before the capacity limit at long context.

Part threethe regimes

When decode becomes compute-bound

Read the max() again: the compute term scales with B while the shared part of the memory term does not. So at large enough batch and short enough context, the compute term wins and decode stops being memory-bound — the regime change the roofline predicts when you push arithmetic intensity right by batching.

RegimeBinding termWhat raises throughput
Small batch, any contextW / BW dominatesBatch harder — the weight read is being amortised across too few tokens
Large batch, long contextB·S·k / BW dominatesShrink KV: fp8 cache, GQA, shorter context. More batch will not help.
Large batch, short contextB·(2N + a·S) / P dominatesNow you are genuinely compute-bound. Lower precision, better kernels, more FLOPS.
Which is why "prefill is compute-bound, decode is memory-bound" needs a caveat

It is true at the batch sizes people usually mean. But decode at batch 256 with a 512-token context is a different regime from decode at batch 4 with 32k — and they want opposite fixes.

Always state the batch and the context alongside the claim.

Using itdrills

Drill yourself

Estimate single-stream decode for a 70B FP16 model on an H100.

3.35 TB/s ÷ 140 GB ≈ 23.9 tok/s. No FLOPS involved — every weight must cross HBM once per token, and that read is the floor.

Quantise to FP8 and model_bytes halves to 70 GB, doubling the ceiling to 47.9 tok/s on the same card.

Why does batching raise throughput at all?

The weight read W is a fixed cost paid once per forward pass and shared across the batch. Emitting B tokens per pass amortises it B ways, turning matrix-vector products into matrix-matrix.

The KV read is not shared, which is exactly what limits the gain.

At S=8,192 on an H200, does adding one more sequence pay?

Barely. It costs 1.342 GB of KV read = 280 µs against only 81.6 µs of added compute, so the memory term dominates and keeps dominating.

Throughput per added sequence falls rather than staying flat — the curve bends almost immediately at long context.

Distinguish the capacity limit from the rate limit on batching.

Capacity: you run out of VRAM for KV and cannot admit more sequences — lesson 07.2's concurrency cap.

Rate: you can still admit them, but each adds more KV read time than throughput. At long context the rate limit bites first.

Your batch is 256 and context is 512. Is decode still memory-bound?

Possibly not. The compute term scales with B while the shared weight read does not, so at large batch and short context B·(2N + a·S)/P can exceed the memory term.

That is the regime change the roofline predicts — batching pushes arithmetic intensity right, and eventually past the ridge. It wants lower precision and better kernels, not less KV.

Someone proposes a faster-compute GPU to fix single-stream latency. Response?

It will not help. Single-stream decode is HBM_bandwidth ÷ model_bytes — FLOPS do not appear. A card with more compute and the same bandwidth gives the same tok/s.

The levers are bandwidth (H100→H200 is 3.35→4.8 TB/s) or fewer bytes (quantisation).
