Module 02 · 02.4 · Kubernetes controllers

The machine
every controller
runs on

Six stages from the API server to your Reconcile function. Each one has a distinct failure mode, and the most-repeated claim about the middle of it is wrong.

Corrects “the DeltaFIFO coalesces events” Centrepiece queue + dirty + processing Verified against client-go 1.33–1.36

Every Kubernetes controller you will ever write or debug runs on the same six-stage conveyor belt. Nothing about it is optional, and every stage has a distinct failure mode. This is the machinery under controller-runtime; knowing it is the difference between "the controller is stuck" and "key ns/foo is wedged in processing because a worker returned without calling Done."

The single most misstated fact in this pipeline

Almost every blog post says the DeltaFIFO coalesces events. It does not. Deduplication happens one layer later, in the workqueue, on keys. Since Kubernetes 1.33 the shared informer does not even use DeltaFIFO by default — and on 1.36 it is unreachable. Details in part three.

Stage onereflector

LIST once, WATCH forever

The reflector is the only component that talks to the API server. Its ListAndWatch loop runs forever under a backoff manager, and the interesting part is the three different ways it can restart.

Why the backoff numbers matter at fleet scale

client-go's comment says these parameters "achieve ~98% traffic reduction when API server is not healthy." If the apiserver falls over, 2,000 reflectors retrying at 0.22 QPS is ≈440 req/s in aggregate, not 2,000/s. The backoff is what makes an apiserver outage recoverable instead of self-sustaining.

Two counter-intuitive details worth memorising

DetailWhy it is backwards from your instinct
Pagination is turned off when resourceVersion != "0" A paginated list skips the watch cache and goes to etcd. The reflector sets pager.PageSize = 0 deliberately — the source comment says "to avoid thundering herd on etcd (e.g. on master upgrades)." Turning paging off to force a cache read is the opposite of the usual instinct.
Bookmarks exist to prevent 410 Gone A BOOKMARK event carries only a resourceVersion and means "you have seen everything up to here." Without it, a watch on a quiet resource sits at a stale RV and 410s on every reconnect, forcing a full relist of everything.

The thundering herd, with real numbers

Practical consequences for your operator: stagger controller restarts, scope caches to the namespaces and label selectors you actually need, and stop being surprised when "everything reconciles slowly for 30 seconds after a fleet-wide rollout" turns out to be every cache refilling at once.

Stage twothe FIFO

The 1.33 change nobody announced

What every blog post says

The DeltaFIFO coalesces the five updates into one, so your handler only sees the latest state.

What actually happens

The FIFO preserves every notification, in order. Deduplication happens one layer later, in the workqueue, on keys.

The DeltaFIFO's only dedup logic is dedupDeltas, and it collapses the last two deltas only, and only when both are deletions — preferring the one carrying a real object over a tombstone. That is the entire mechanism. Read it once and you will never overclaim again.

Worse, the DeltaFIFO had a subtle defect: because it queues per key, a key already in the queue keeps its original position while newer deltas pile onto it. So object B's change at t=2 can be delivered before object A's change at t=3, even though A's earlier change is what put A in the queue. It reorders events across objects.

Say this in an interview

Not "the DeltaFIFO coalesces the updates." Say: "The FIFO preserves every notification in order; deduplication happens one layer later, in the workqueue, on keys." On any cluster at 1.33+ the first version is wrong, and on 1.36 the DeltaFIFO is not even in the path.

Stage threeordering

Store first, handlers second

Pop holds the FIFO lock while your handler runs

Which is why a slow event handler stalls the entire informer. client-go emits a trace when the queue is deeper than 10 and one item takes over 100 ms, with the literal reason string "slow event handlers blocking the queue". That was added after a report of informer memory reaching 2.3 GB in 30 minutes with pods churning every 10 seconds.

Stage fourkeys, not objects

The deepest idea in the module

Your event handlers should do almost nothing: derive a key and enqueue it. Three reasons, and together they are what makes level-triggered reconciliation true at the plumbing layer rather than merely a design intention.

  1. Dedup sets.Set[T]

    The workqueue stores keys in a set, so ten changes to one object collapse to one entry. Enqueue the object and every enqueue is a distinct value — nothing collapses. Since the FIFO does not coalesce, the workqueue is the only place dedup happens anywhere in the pipeline.

  2. Freshness lister.Get(key)

    When a worker finally pops the key, it re-reads current state. Enqueue the object and you freeze a snapshot at enqueue time, then reconcile it after the world has moved on.

  3. Level-triggered semantics reconcile(name)

    You reconcile toward "what should be true for this name," not "replay this event." Missing an intermediate event becomes harmless by construction.

  4. And a practical fourth [T comparable]

    The workqueue's type parameter requires comparability. A *v1.Pod is comparable but useless as a dedup key; a v1.Pod struct is not comparable at all and will not compile.

The classic first-controller panic

Replace() synthesises deletions as DeletedFinalStateUnknown{key, lastKnownObject}. A DeleteFunc that blindly type-asserts to *v1.Pod panics the moment a relist happens. Use DeletionHandlingMetaNamespaceKeyFunc, always.

What that buys you: 1,001 events, 2 reconciles

The failure modeDone vs Forget

How one key goes permanently deaf

Done(item) is the only thing that removes a key from processing. Skip it — an early return before the defer, a panic with no recover, a Reconcile blocked forever on an HTTP call with no context deadline — and here is the exact cascade:

  1. The key stays in processing forever

    Nothing else will ever remove it.

  2. Every future Add(k) becomes a silent no-op

    It inserts into dirty, sees processing.Has(k), and returns without pushing. The key is now permanently invisible to Get.

  3. That one object stops reconciling — for the life of the process

    Every other object keeps working perfectly, which is what makes this so vicious to diagnose. Your controller is not "down." It is deaf to exactly one key.

  4. Two metrics climb linearly forever workqueue_unfinished_work_seconds · workqueue_longest_running_processor_seconds

    That pair is the fingerprint. Learn it.

  5. Shutdown hangs until SIGKILL

    ShutDownWithDrain() waits for processing.Len() == 0, so the pod blocks until terminationGracePeriodSeconds expires.

Forget and Done are not alternatives

The source comment settles it: "This only clears the rateLimiter, you still have to call Done on the queue." Forget touches the backoff bookkeeping. Done touches the queue. You need both, and they fire on different conditions.

The delaying layer, briefly

AddAfter(item, d) does not sleep. It pushes a waitFor{data, readyAt} into waitingLoop, which keeps a min-heap ordered by readyAt plus an item→entry map. Re-adding an item already waiting does not duplicate it — insert() keeps the earlier readyAt. When the time passes, the item goes onto the base queue through the ordinary Add, so it re-enters the three-set dance and dedupes normally.

Drill yourself

Five updates to one Pod arrive before the consumer drains. How many deltas, how many reconciles?

Five deltas — the FIFO does not coalesce. But one or two reconciles, because the handler enqueues the same key five times and the workqueue's dirty set collapses them.

If a worker was already holding the key, all five collapse into a single dirty bit, and Done() converts that into exactly one re-queue.

A worker panics before calling Done. What breaks, and what keeps working?

That one key stops reconciling permanently. Every other key keeps working normally — which is why this looks like "the controller is fine, but this one object is ignored."

Fingerprint: workqueue_unfinished_work_seconds and workqueue_longest_running_processor_seconds climbing linearly forever. Shutdown will also hang, because ShutDownWithDrain waits for processing to empty.

Why does the reflector turn off pagination when resuming from a resourceVersion?

Because a paginated LIST skips the apiserver's watch cache and reads from etcd. Setting pager.PageSize = 0 forces the cheap watch-cache path. The source comment: "to avoid thundering herd on etcd (e.g. on master upgrades)."

Your DeleteFunc panics type-asserting to *v1.Pod. When, and why?

After a relist. Replace() synthesises deletions for keys the store knew about but the new list lacks, wrapped as DeletedFinalStateUnknown{key, lastKnownObject} — not as the object itself.

Fix: cache.DeletionHandlingMetaNamespaceKeyFunc, which unwraps the tombstone.

Where does deduplication happen in this pipeline, and where does it definitely not?

It happens in the workqueue, on keys, via the dirty set.

It does not happen in the FIFO. The DeltaFIFO's only dedup is dedupDeltas, which collapses the last two deltas and only when both are deletions. And since 1.33 the default is RealFIFO, which does no per-key grouping at all.

Why enqueue a key rather than the object you already have in hand?

Dedup (keys collapse in a set, objects do not), freshness (the worker re-reads current state instead of a frozen snapshot), and level-triggered semantics (you reconcile toward a name, so missed intermediate events are harmless).

Plus the mechanical reason: the queue is [T comparable], and a v1.Pod struct is not comparable.

What to keep

  • One talkerThe reflector is the only component that touches the apiserver. Everything else reads a local cache.
  • FIFO preservesEvery notification, in order. No coalescing. RealFIFO since 1.33, locked GA at 1.36.
  • Store then notifyprocessDeltas writes the indexer before calling handlers, so a worker reading the lister sees at least the triggering state.
  • Keys, never objectsDedup, freshness, and level-triggered semantics all come from this one choice.
  • Three setsqueue + dirty + processing. A key is never processed twice concurrently; a change during processing is never lost.
  • Done alwaysDeferred, on line two. Skipping it makes exactly one key permanently deaf while everything else looks healthy.
  • Forget on successDifferent job from Done — it resets backoff bookkeeping, not queue state.
  • 410 is normalA relist re-delivers everything and synthesises tombstones. Handle them, and expect the reconcile spike.
