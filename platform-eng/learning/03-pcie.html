The link that
trained low and
told nobody

A degraded PCIe link keeps working at a fraction of spec, and no GPU or NIC counter mentions it. Four lines of lspci separate a real fault from the topology you built.

Fault signature LnkSta < LnkCap, same device Most-missed case LnkCtl2 target set by software Why it matters it rebinds 09.1's bottleneck

A PCIe link can silently train to a lower generation or width, and the GPU still works — at a fraction of spec, with nothing in the GPU's own counters explaining why. Lesson 09.1 showed the NIC binds by only 8% over usable PCIe, so a degraded link moves the bottleneck without any config changing. This is how you catch it.

Part onethe numbers

Rate, lanes, and the code tax

Bandwidth is per-lane rate × lanes, quoted per direction. The per-lane rate is the signalling rate times the line code's efficiency — and line coding exists because the receiver recovers its clock from the data stream, so the encoding must guarantee transitions.

Two facts to state instantly

Each generation doubles the per-lane rate; halving the width halves bandwidth. So Gen5 x16 vs Gen3 x16 is 4×, and Gen5 x16 vs Gen3 x8 is 8×.

The LnkSta speed field is raw GT/s, not the generation. 2.5=Gen1, 5=Gen2, 8=Gen3, 16=Gen4, 32=Gen5, 64=Gen6. Train yourself to read GT/s and map it, because that is what the tool prints.

Part twothe core skill

LnkCap versus LnkSta

LineWhat it tells you
LnkCapThis device's own advertised maximum. It is not the negotiated minimum of both ends — each end advertises independently. To find which hop caps a chain you must read LnkCap at every hop.
LnkStaWhat actually trained. Compare against LnkCap at both ends.
LnkCap2The full speed vector. If this reads 2.5-16GT/s on a card you believe is Gen5, the device is the cap, not the channel.
LnkCtl2The ceiling software requested. Reading 16GT/s while LnkCap2 supports 32 means something set it — firmware, a driver, a manual setpci. A configuration fault, not a hardware one, and the case people misdiagnose most often.
The two cases that produce false positives and false negatives

ASPM idle downtraining is not a fault. With power management enabled an idle link may drop to a low-power state and retrain on exit. A 2.5GT/s reading on an idle card can be entirely benign — re-check under real load, or confirm LnkCtl: ASPM Disabled, which is what most server GPUs ship with.

A reduced LnkCap is a configuration fact; LnkSta below a full LnkCap is a fault. A Gen5 GPU behind a Gen4-only switch trains to Gen4 with no (downgraded) marker, because neither end was capable of more on that segment. That is topology, not defect. Same for a bifurcated root port advertising Width x8.

The fault signature, stated exactly

LnkSta < LnkCap on the same device. Anything else is either the topology you built or the configuration someone applied.

And lspci -vvv needs root to read the capability block — without it these lines are blank or <access denied>, which is not the same as healthy.

Part threewhat it costs

Why this matters two lessons later

Using itdrills

Drill yourself

LnkSta: Speed 16GT/s on a Gen5 GPU. Fault or not?

Depends entirely on LnkCap at both ends. If the GPU's own LnkCap says 32GT/s, that is a fault. If it sits behind a Gen4-only switch whose downstream port advertises 16GT/s, the link is doing exactly what the topology permits and there is no (downgraded) marker.

The fault signature is specifically LnkSta < LnkCap on the same device.

LnkCap2 supports 2.5–32GT/s but LnkCtl2 says Target 16GT/s. What happened?

Something set it — firmware, a driver, or a manual setpci. The hardware is capable; software requested a lower ceiling.

This is a configuration fault, not a hardware one, and it is the case people misdiagnose most often — because the link looks "trained correctly" against the target it was told to hit.

An idle GPU shows 2.5GT/s. Raise an RMA?

No — re-check under load first. With ASPM enabled an idle link legitimately drops to a low-power state and retrains on exit.

Confirm with LnkCtl: ASPM Disabled, which is what most server GPUs ship with; if ASPM really is disabled and it still reads 2.5GT/s under load, then it is real.

How much faster is Gen5 x16 than Gen3 x8?

8×. Two generation doublings (Gen3→4→5) is 4×, and doubling the width from x8 to x16 is another 2×.

63.02 vs 7.88 GB/s per direction.

Why does Gen6 lose 5.5% to overhead that Gen5 never paid?

PAM4 signalling needs FEC. Each 256-byte FLIT carries 8 bytes CRC and 6 bytes FEC, so payload efficiency is 242/256 = 94.5% against Gen5's 128b/130b at 98.46%.

It gains elsewhere: no sync headers, and DLLPs absorbed into the flit rather than interleaved as separate packets — so for small transfers it beats the naive rate ratio.

Your 400G NIC delivers ~27 GB/s and its own counters look clean. Where do you look?

lspci -vvv on the NIC and on every hop up to the root port. A Gen5 x8 link gives ~27 GB/s usable, which caps a 50 GB/s NIC at just over half.

Nothing in the NIC's counters or nvidia-smi reports this — the bottleneck moved from the wire to the bus, and only LnkSta vs LnkCap shows it.

  • LnkSta < LnkCapThe fault signature, on the same device. Everything else is topology or configuration.

  • LnkCtl2 is softwareA lowered target speed is a config fault. The most-missed case.
  • ASPM idles legitimatelyRe-check under load before calling a low idle speed a defect.
