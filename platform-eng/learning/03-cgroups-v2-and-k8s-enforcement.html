Lesson 01b.1 ended on a mismatch of granularity: cgroup limits apply to a set of tasks, while the scheduler acts on individuals. This is the lesson where that gap becomes a YAML field, a kernel file, and a 93-millisecond stall.

Part onestructure

Four rules that explain every “why can't I just…”

  1. Availability is set by your parent cgroup.controllers

    Read-only. It lists which controllers are usable in this cgroup, and the parent decides what appears there.

  2. Enablement flows top-down cgroup.subtree_control

    A controller acts on a cgroup's children only if that cgroup lists it here. echo "+cpu +memory -io" > cgroup.subtree_control.

  3. No internal processes

    A non-root cgroup with domain controllers enabled may not contain processes of its own. Processes live only on leaves.

  4. Delegation hands you a subtree, not your own ceiling

    Which is exactly why the kubelet can be given a subtree without being able to raise the limits above it.

The consequence of rule 2 that catches everyone

The interface files in a directory are owned by its parent, not by itself. cpu.max appears in cgroup C because C's parent enabled cpu in its subtree_control. Anything not prefixed cgroup. is a knob your parent is using to constrain you.

Why rule 3 exists — arithmetic, not aesthetics

If cgroup P held both a child cgroup C (weight 100) and its own bare processes, the CPU controller would have to decide how those processes compete against C. There is no principled answer, because bare processes have no weight of their own. The rule rules the question out of existence.

Practically: to start controlling a populated cgroup you must first create children, move every process into them, then enable controllers. That is precisely the dance the kubelet does at startup, and why kubepods.slice is empty of processes while its descendants are not.

Part threethrottling

Why low average CPU still throttles

The problem the kernel is solving: charge CPU time against a per-cgroup budget on a many-core machine without taking a global lock on every context switch. A naive shared counter would ping-pong a cache line across sockets thousands of times a second.

The design: a global pool per cgroup, refilled to quota at each period boundary, transferring budget to per-CPU silos in fixed-size slices on demand.

Now watch a well-behaved app get wrecked by it. The pod asks for 2 CPUs and runs 32 threads on a 64-core node — a completely ordinary shape for a data loader or a JVM.

This is the ticket you will actually get

“The pod is nowhere near its CPU limit but latency is terrible.” Both halves are true. Average utilisation is 5%; p99 latency is 10× the work. The metric that shows it is nr_throttled / throttled_usec in cpu.stat — never average CPU.

The fixes are: fewer threads, a higher limit, a shorter --cpu-cfs-quota-period, or no CPU limit at all with requests doing the work. Not "add more cores" — the 62 idle ones were unusable by construction.

Part fourthe visibility gap

What the container sees vs what the kernel enforces

A process inside a container reads nproc, /proc/cpuinfo and /proc/meminfo and sees the host's hardware. Nothing virtualises them — the cgroup namespace from lesson 02 hides the cgroup path, not the hardware numbers, and there is no "hardware namespace."

The correct fix is always the same shape: make the runtime read /sys/fs/cgroup/cpu.max and memory.max, or use a cgroup-aware runtime version. lxcfs papers over it by bind-mounting a synthesised /proc/meminfo, which helps naive tools but is not the mechanism.

Part fivememory

Without MemoryQoS there is only the cliff

The default state of most clusters

MemoryQoS (feature gate MemoryQoS, alpha since v1.27, beta at v1.37) is what makes the kubelet write memory.min / memory.low / memory.high at all. Without it, a Kubernetes memory limit sets memory.max and nothing else — no soft throttle, only the OOM cliff.

Using itdrills

Drill yourself

A pod's average CPU is 5% and its p99 latency is 10× its work. Where do you look?

cpu.stat — specifically nr_throttled and throttled_usec. Average CPU cannot show this by construction.

The shape: many threads drain the global pool in a few milliseconds, then every thread is dequeued for the rest of the 100 ms period. 32 threads against a 2-CPU quota exhaust 200 ms of budget in 6.25 ms of wall clock.

Does requests.cpu cap anything at runtime?

No. It is a scheduler bin-packing reservation, never re-read after placement. At runtime it becomes cpu.weight, which only matters under contention and only relative to siblings.

limits.cpu is the cap, via cpu.max.

You read cpu.weight at the pod slice and at the container scope for the same 500m request, and get 20 and 59. Bug?

No. The kubelet's getCPUWeight and runc's ConvertCPUSharesToCgroupV2Value use different formulas on the same 512 shares.

Both are valid because weights only mean anything relative to siblings at the same level. The absolute numbers are not comparable across levels.

Why can't kubepods.slice hold processes directly?

Rule 3 — no internal processes. A non-root cgroup with domain controllers enabled in subtree_control may not contain its own processes, because bare processes have no weight and there is no principled way to make them compete against a weighted child cgroup.

Your JVM sizes its heap for 256 GiB inside an 8 GiB container. Why, and what's the fix?

Nothing virtualises /proc/meminfo. The cgroup namespace hides the cgroup path, not the hardware numbers, and no "hardware namespace" exists.

Fix: a cgroup-aware runtime that reads /sys/fs/cgroup/memory.max. lxcfs can synthesise a fake /proc/meminfo, which helps naive tools but treats the symptom.

You set limits.memory: 8Gi. What did the kernel actually get?

memory.max = 8589934592, and — unless MemoryQoS is enabled — nothing else. No memory.high, no soft throttle, no reclaim pressure short of the limit. Just the cliff.

That is the default on most clusters today.
