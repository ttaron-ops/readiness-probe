Part onethe object

What a process actually is

Start by deleting the sentence you already have, because it is the thing standing between you and everything else.

Delete this

A process is a running program. The kernel keeps a list of programs it is running, and each one has a PID.

Install this

The kernel schedules threads. Each one is a struct task_struct. A “process” is just a group of them that share an ID and an address space.

There is no struct program in the kernel. There is no struct process either. There is exactly one relevant object — struct task_struct — and the kernel creates one per thread.

When the scheduler runs, it does not look at a list of programs. It looks at a run queue of task_structs and picks one. That is the only granularity it has.

So where does “process” come from?

It is an emergent grouping, not an object. A set of task_structs counts as one process when they share three things: a thread-group ID, an address space, and a signal state.

Every task_struct carries two ID fields, and this is the single most useful thing to memorise in part one:

FieldUserspace calls itWhat it identifiesRead it with
pidTID — thread ID This one specific thread. Unique kernel-wide. gettid()
tgidPID — “the process ID” The whole thread group. Equals pid for the group leader. getpid()

Read that table twice. The kernel field named pid is not what you call a PID. The kernel field named tgid is. That off-by-one-name is responsible for an enormous amount of confusion, and once you see it, ps output stops being ambiguous forever.

Shared or private: the fields that define the grouping

What makes those four tasks “one process” is that clone() was told to share certain pointers. Change which pointers are shared, and you change what kind of thing you created — a thread, a process, or a container.

Shared across a thread group
  • mm — address space, one page table
  • files — the fd table
  • fs — cwd and root
  • signal — process-wide signal state
  • tgid — the group identity itself
Private to each task_struct
  • pid — its own TID
  • __state — its own state → part two
  • se — scheduler keys, own run queue slot
  • stack — its own kernel stack
  • pending — per-thread signal queue

/proc is a rendering of task_struct

/proc is not a database the kernel maintains alongside its real state. It is a live view onto task_struct, generated when you read it. That reframe matters because it tells you where to look for anything:

PathShows you
/proc/<tgid>/The group leader's task_struct, plus process-wide aggregates
/proc/<tgid>/task/One directory per task_struct in the group — the real thread list
/proc/<tgid>/statusTgid, Pid, Threads, signal masks, memory counters
/proc/<tgid>/wchanThe kernel function this task is asleep in → part two
/proc/<tgid>/ns/The nsproxy pointers — namespace membership → lesson 02
/proc/<tgid>/cgroupThe css_set — cgroup membership → lesson 03

Why this framing is the whole module

Two fields on task_struct are the entire container abstraction:

  • nsproxy — a pointer table to this task's namespaces (PID, mount, net, IPC, UTS, user).
  • cgroups — which cgroup node this task is attached to, per controller.

A container is not a new kind of object. It is ordinary task_structs whose nsproxy and cgroups pointers happen to point somewhere private.

The plural matters

A container is a set of task_structs, not one. Usually a whole process tree — an init-ish PID 1, its children, and all of their threads.

Nobody enumerates that set. It falls out of clone(): a child that doesn't ask for new namespaces inherits its parent's nsproxy and css_set pointers by reference count. The runtime does the private-pointer setup once, on the first task, and every descendant is a member for free.

Keep the three groupings distinct, because they nest and people collapse them:

GroupingDefined byTypical size
Thread group (a “process”)shared tgid + mm1–100 tasks
Containershared nsproxy + cgroupsmany processes
Run queue (what the scheduler sees)one CPU's runnable tasksindividual tasks
Where you will use this

When you set resources.limits.cpu: 2 on a Kubernetes pod, you are not telling the scheduler to run two threads. You are writing a bandwidth quota onto a cgroup node that throttles a set of independently scheduled tasks collectively. An 8-thread container under a 2-CPU limit gets throttled hard, and the reason is exactly this mismatch of granularity: limits are per-set, scheduling is per-task.

Part twothe state machine

How the kernel moves it around

Same move as before: delete a sentence first.

Delete this

A task's state is one value from a list — running, sleeping, stopped. Checking it means comparing for equality.

Install this

__state is a bitmask — a row of independent switches packed into one integer. Checking it means masking: state & X.

The tell is in the constants. They are all powers of two, which is deliberately wasteful for an enum and exactly right for a bitmask — each name gets a private bit column, so names can be OR'd together without colliding.

The base states — one bit each, roughly exclusive

TASK_RUNNING0x0000 000000000000 no bits at all — running or queued
TASK_INTERRUPTIBLE0x0001 000000000001 sleeping, any signal wakes it
TASK_UNINTERRUPTIBLE0x0002 000000000010 sleeping, signals not delivered
__TASK_STOPPED0x0004 000000000100 SIGSTOP / SIGTSTP
__TASK_TRACED0x0008 000000001000 stopped by a debugger
EXIT_ZOMBIE0x0020 000000100000 exited, parent hasn't reaped it
base state bit setclear

The modifier bits — policy switches, orthogonal to the base state

TASK_WAKEKILL0x0100 000100000000 a fatal signal may break this sleep
TASK_NOLOAD0x0400 010000000000 do not count me in load average
modifier bit setclear

The two compositions that matter operationally

TASK_KILLABLE0x0102 000100000010 = UNINTERRUPTIBLE | WAKEKILL
TASK_IDLE0x0402 010000000010 = UNINTERRUPTIBLE | NOLOAD
base statemodifierclear

Neither of those is a new state. Both are TASK_UNINTERRUPTIBLE with one extra switch flipped. That is what “compositions of bits” means, and it is why the enum model fails: with an enum you would need a distinct entry for every combination, and every switch statement in the kernel would need updating whenever someone added an orthogonal property.

With bits, each consumer masks for the one bit it cares about and ignores the rest:

The trap this sets

Rows three and four are the same letter and opposite answers on the column that decides whether your kill -9 lands. “The process is in D” is not a complete description of its state — it describes the low byte. The bits that determine what you can do about it are in the high byte, and ps discarded them before printing anything.

Watching a task move through the machine

R hides the distinction you most want

“Executing on a CPU right now” and “sitting on a run queue while something else executes” are the same letter. This is why run-queue latency is invisible to ps — a starved thread and a busy thread look identical. To see the difference you need /proc/<pid>/schedstat field 2 (run_delay, nanoseconds spent waiting for a CPU) or scheduler tracing.

Z: not a process, a receipt

So a thousand zombies is not a load problem or a memory problem. It is a broken parent that stopped calling wait(), and the only resource being exhausted is PID numbers.

D: why it exists, and why kill -9 seems to fail

When a task submits I/O it is holding kernel state that must be unwound in a specific order — a page locked for writeback, an open filesystem transaction, a reserved RPC slot, a device queue entry in flight. If a signal could yank the task out at an arbitrary point, every one of those code paths would need its own safe abort-and-restart logic. An enormous, error-prone surface.

TASK_UNINTERRUPTIBLE is the kernel declining that complexity: “this sleep is short and bounded, do not make me handle interruption here.” The pathology is that “short and bounded” stops being true the moment the NFS server or the NVMe controller stops answering.

What kill -9 actually does

SIGKILL is not magic and does not bypass anything. It is two steps:

  1. Set a bit in the target's pending-signal set.
  2. Call signal_wake_up() to try to wake it.

Step 2 only wakes a sleeper whose state includes TASK_WAKEKILL or TASK_INTERRUPTIBLE. Plain TASK_UNINTERRUPTIBLE matches neither — so the signal stays queued and is delivered the instant the task next heads back toward userspace, which happens only after the I/O completes or times out.

The reframe worth memorising

kill -9 on a D-state process did not fail. It queued perfectly and is waiting its turn. Check ShdPnd in /proc/<pid>/status and you can see the bit sitting there. Nothing is broken; the task simply cannot be woken to receive it.

TASK_KILLABLE resolves the folklore

Two camps both insist they are right about NFS: one says kill -9 never works on a hung mount, the other says it usually does. Both are reporting real experience, on different code paths.

TASK_KILLABLE was introduced so long-latency network filesystems could still be escaped. Ordinary signals are still ignored; a fatal one breaks the sleep. Modern NFS uses killable sleeps in most of its RPC wait paths — so on a current kernel kill -9 often does work, while the folklore was formed on kernels where it didn't. It still shows as D either way, because TASK_WAKEKILL is masked off before the letter is chosen.

The practical consequence: wchan tells you which case you are in. A task in rpc_wait_bit_killable will die on kill -9. A task in nfs_wait_on_request will not.

TASK_IDLE is why your load isn't 200

A modern kernel runs many worker threads (kworker/*, nfsd, xfs-*) that sit in uninterruptible sleep waiting for work — semantically idle, but historically counted as load. TASK_IDLE gives them the safety of an uninterruptible sleep plus an explicit “don't count me” bit.

Which sets up the next concept exactly: load average counts nr_running + nr_uninterruptible, and D-state tasks are in that second term. A node with load 80 and 3% CPU is not CPU-saturated — it has ~80 tasks parked in D on a storage path.

Part threeusing it

How you will actually use this

Both concepts converge on one workflow: someone says “the node is wedged,” and you have to turn that into a falsifiable claim about a specific state in a specific kernel path. Five steps, in order.

  1. Split runnable from blocked cat /proc/loadavg

    Compare the numerator of field 4 against the three floats. 41.9 40.2 33.7 1/2203 means the smoothed count is ~42 but only 1 task is runnable — so ~41 are in D. You have localized the incident to the I/O path before running anything else.

  2. Confirm with the state letters ps -eo stat --no-headers | sort | uniq -c | sort -rn

    Count the D's directly. Remember to discount I — those are idle workers and mean nothing.

  3. Name the exact kernel path ps -eo pid,stat,wchan:32,comm | awk '$2 ~ /D/'

    This is the step that turns “stuck” into an incident report. nfs_wait_on_request, rpc_wait_bit_killable, blk_mq_get_tag, io_schedule — each names a different subsystem and a different owner. It also tells you whether kill -9 will work.

  4. Prove they aren't computing cat /proc/<pid>/stat · /proc/<pid>/schedstat

    D-state tasks burn no CPU. Near-zero utime/stime alongside a high load number is the arithmetic proof that load is counting waiters, not workers. For the tasks that are in R, schedstat field 2 gives run-queue latency in nanoseconds.

  5. Confirm the resource cat /proc/pressure/{cpu,io,memory}

    Load average is not a saturation metric. PSI measures wall-clock time work spent waiting. io full 97% alongside cpu some 0.4% closes the case: storage incident presenting as a compute symptom.

The one-sentence version

“Load 42 with one runnable task means 41 tasks in uninterruptible sleep; their wchan is in the NFS RPC path, they've consumed 70 ms of CPU between them, and io.pressure full is 97% — this is a storage incident presenting as a compute symptom.”

Three things that follow directly

SituationWhat the model tells you
A node won't drain The kubelet cannot terminate D-state tasks either. It is not a Kubernetes bug — no userspace process can kill something that cannot be woken. Fix the storage path.
“Which thread is the problem?” ps shows thread groups by default and will hide it. Use ps -eLo or top -H. A 40-thread process with one pegged thread looks 2.5% busy at process granularity.
Distributed training stalls, GPUs idle A synchronous all-reduce completes only when its slowest participant arrives. One CPU-side thread (data loader, NCCL proxy) delayed on a run queue delays every GPU in the job. Per-task latency, not per-process.

Drill yourself

If these come out cold, both concepts are solid.

Process P has 4 threads. How many task_structs, how many mm_structs, and what does getpid() return in thread 3?

Four task_structs, one mm_struct. getpid() returns the TGID — the same value in all four threads. To get thread 3's own identity you need gettid().

PID 24601 is in D. You run kill -9 24601 and nothing happens. Where is the signal right now?

In the process-wide pending set — visible as a set bit in ShdPnd in /proc/24601/status. It was queued successfully. signal_wake_up() declined to wake the task because its state includes neither TASK_WAKEKILL nor TASK_INTERRUPTIBLE.

It will be delivered the moment the task next returns toward userspace — which requires the I/O to complete or time out first.

Two processes both show D. One dies on kill -9, one doesn't. Same letter — what differs?

Bit 8, TASK_WAKEKILL (0x0100). The one that dies is in TASK_KILLABLE (0x0102); the other is in plain TASK_UNINTERRUPTIBLE (0x0002). ps masks that bit off before choosing the letter, so both print D.

wchan is how you tell them apart in practice.

Why doesn't I count toward load average, and which bit says so?

TASK_NOLOAD (0x0400). The load accounting condition in kernel/sched/core.c requires TASK_UNINTERRUPTIBLE set and TASK_NOLOAD clear. TASK_IDLE is 0x0402 — uninterruptible for safety, excluded from load by policy.

Load is 80, CPU is 3%. One-line diagnosis, and which file confirms it?

Roughly 80 tasks in uninterruptible sleep on a blocked I/O path — almost certainly storage. /proc/loadavg confirms the split immediately: field 4's numerator will be near zero while the floats sit near 80.

Then wchan on the D-state tasks names the subsystem, and /proc/pressure/io confirms the resource.

Is a container a single schedulable entity?

No. A container is a set of task_structs sharing nsproxy and cgroups pointers — normally a whole process tree, each process with its own threads. The scheduler has no concept of “container” at all; it schedules individual tasks.

The sentence “a container is an ordinary task_struct with private pointers” answers what kind of object, not how many.

What to keep

  • One per threadtask_struct is the unit of scheduling. A process is a group of them; a container is a much bigger group of them.
  • pid ≠ PIDThe kernel field pid is the thread ID. The kernel field tgid is what userspace calls the PID.
  • /proc is a viewNot a separate database — a live rendering of task_struct fields, generated on read.
  • State is bitsBase state in the low byte, orthogonal policy switches in the high byte. Always mask, never compare.
  • The letter liesThe bits that decide whether you can kill it are masked off before ps picks a letter. Read wchan.
  • kill -9 queuesIt never fails. It sets a bit in ShdPnd and tries to wake. A plain D sleeper cannot be woken.
  • D is counted, I is notLoad is nr_running + nr_uninterruptible, minus everything carrying TASK_NOLOAD.
  • Per-set vs per-taskcgroup limits apply to a set; the scheduler acts on individuals. Lesson 03 is built entirely on that gap.
